# Product Roadmap v4 - Cycle 08.1

## PWA Installability & Role-Aware App Experience

Cycle 08.1 turns Aruka into one installable PWA with one deploy, one manifest and one service worker. The installed app name is `Aruka`; professional and student differences live in authenticated UX and install copy, not in separate apps.

## Architecture

- Single PWA: yes.
- Manifest name: `Aruka`.
- Start URL: `/`.
- Scope: `/`.
- Display: `standalone`.
- Orientation: `any`.
- Professional route after auth: existing `/dashboard` flow.
- Student route after auth: existing `/minha-area` flow.

The installed launch intentionally starts at `/` so the current auth/session and role routing decide the correct destination.

## Manifest And Icons

The manifest is configured through `vite-plugin-pwa`. Icons are derived from `public/app-icon-1024.png` without redesigning the brand:

- `public/pwa/icon-192.png`
- `public/pwa/icon-512.png`
- `public/pwa/maskable-icon-192.png`
- `public/pwa/maskable-icon-512.png`
- `public/pwa/apple-touch-icon.png`

Maskable icons use padding and a light Aruka-compatible background to avoid unsafe cropping.

## Service Worker And Cache Policy

The service worker is generated by `vite-plugin-pwa` with prompt-based updates. Static app-shell assets and versioned build files may be precached.

Runtime caching is intentionally empty:

- Supabase API/auth: network only.
- Student data: not cached by service worker.
- Professional data: not cached by service worker.
- Financeiro/history/execution payloads: not cached by service worker.
- YouTube/youtube-nocookie/iframes/videos: not cached by service worker.

This keeps cross-user devices safe when a professional logs out and a student logs in, or the reverse.

## Install Prompt

`PwaExperienceManager` is mounted only inside authenticated surfaces:

- Professional shell: role `professional`.
- Student `MinhaArea`: role `student`.

The prompt appears after authenticated home render plus a short delay. It never appears on `/login`, never appears in standalone mode and respects a device-level dismissal key:

`aruka_pwa_install_hide_banner`

The hide preference controls only the automatic internal banner. Manual install entry points remain available while the app is running in browser mode and is not standalone.

Professional copy focuses on management. Student copy focuses on training, videos, history and timer.

## Platform Behavior

Android and Chromium desktop use `beforeinstallprompt` when the browser provides it. The event is kept only in memory and `prompt()` is called only after user action.

Chrome controls `beforeinstallprompt`, native prompt availability and native banner reappearance. Chrome can omit the event, stop emitting it after a cancellation, apply engagement/elegibility heuristics or delay its own native banner. This is not treated as an Aruka failure. Aruka mitigates it with install discovery independent of the event, persistent install shortcuts in browser mode and an internal manual guidance fallback.

iOS Safari does not support `beforeinstallprompt`; Aruka shows manual guidance instead: Share, then Add to Home Screen. The iOS CTA is informational, not a fake install button.

Unsupported browsers do not receive a broken install CTA.

## Update Safety

Updates are prompt-based. Aruka does not auto-reload when a new service worker is waiting.

For active student workout sessions, the update prompt is deferred. For professional forms, there is no global dirty-state contract yet, so the first implementation uses explicit user action only and never forces reload.

## Auth And Session

Supabase session restore remains browser-storage based through the existing client. The PWA service worker does not intercept or cache Supabase API/auth responses.

Logout signs out normally; the PWA remains installed and reopening the app returns to login unless a valid session exists.

## Offline Limits

PWA installability is not offline-first. The app shell may load from cache, but login, workout execution, finance, history and data sync require network access to Supabase.

The workout rest timer remains logically correct because it uses an absolute `restEndsAt` deadline and recalculates on focus/pageshow/visibility changes. Cycle 08.1 does not promise continuous JavaScript execution or background notifications while the device is locked.
